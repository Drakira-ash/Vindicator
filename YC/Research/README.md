# Unity 组件式 Unit 架构调研（2026-10-28）

调研范围：能力系统（Ability）、属性系统（Stats）、寻路（Pathfinding）。
目标：为本项目 `Assets/Script/Unit` 的「防御塔 / 敌人」组件式实现提供依据。

## 结论摘要

1. **数据与运行时分离**：所有配置（属性/能力/单位模板）用 ScriptableObject 定义，运行时另建可变实例；**绝不直接修改 SO 资产**（Play Mode 下的修改会持久化）。
2. **属性系统采用固定计算管线**：`base → 加法固定值 → 加法百分比 → 乘法百分比 → 覆盖 → clamp`，按来源（装备/增益/等级）标记修正，便于移除；脏标记 + 惰性重算，变更事件驱动 UI。
3. **能力用「定义 + 行为组件」**：能力定义是 SO（冷却/消耗/参数），能力行为是挂在单位上的 MonoBehaviour 组件（函数实现）；中央组件负责授权与调度，而非把所有逻辑塞进一个 CharacterController。
4. **固定路线塔防用路点/样条，不用 NavMesh**：多份资料一致认为固定路线的 TD 用 waypoints 最便宜、最可控；NavMesh 适合开放区域或障碍动态变化。到达阈值需略大于单帧位移，避免抖动；多路线时每个敌人持有自己的路线引用。
5. **目标搜索不要每帧 `FindGameObjectsWithTag`**：单位生成时注册、死亡时注销，从共享列表里选目标。

## 对项目的取舍

| 议题 | 决定 | 理由 |
|---|---|---|
| 能力实现 | 抽象 `UnitAbility` MonoBehaviour + `AttackAbility` 等具体组件 | 满足「能力集是行为的函数」，可组合、可在 Inspector 配置 |
| 属性实现 | `UnitDefinition`(SO) + 运行时 `StatBlock`（枚举键 + 修正列表） | 数据驱动、可共享模板、运行时不污染资产 |
| 寻路 | 场景内路点路线（`UnitRoute`）+ 样条插值 + 向下射线贴地 | 固定路线 TD 最佳实践；射线贴地可直接处理斜坡 |
| 仇恨/转目标 | 单位注册表 + 最近可攻击目标；目标死亡事件触发重新选目标 | 避免每帧全局搜索 |
| 不采用 | EX-GAS 等完整 GAS 框架 | 依赖 Odin、体量大、自述有较多 bug/性能问题，超出当前需求 |
